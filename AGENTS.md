# AGENTS.md

## Purpose

This repository is a Go CLI for checking Ubuntu APT sources before an upgrade. The product behavior is defined by the documentation and the Makefile, not by loose assumptions.

Read [README.md](README.md) for user-facing behavior and [Makefile](Makefile) for the canonical build, test, and release workflow.

## Project map

- CLI entry point: cmd/ppa-utils/main.go
- Command packages: internal/cli/commands/<name>
- Shared command setup: internal/cli/root
- APT parsing and source files: internal/ppa
- Ubuntu release detection: internal/distinfo
- Interactive terminal UI: internal/cli/tui
- Generic prompts and confirmations: internal/cli/clitext

## Rules for agents

1. Follow the existing Cobra + Options command pattern.
   - Keep command logic in per-command packages.
   - Prefer small helpers and run(opts) over large inline logic.
   - Do not add unrelated behavior to main.go.

2. Match the repo’s conventions before inventing a new pattern.
   - Reuse command structure and naming rather than creating a new abstraction.
   - Keep behavior consistent with the current CLI flags and output style.

3. Treat user-facing docs as the source of truth.
   - Use README.md for command semantics and examples.
   - Use Makefile targets for validation and build steps.
   - Do not duplicate or contradict the README in code comments or agent instructions.

4. Preserve safety for system files.
   - Any write to /etc/apt or other system directories must be explicit, root-aware, and dry-run-friendly when applicable.
   - Keep the existing safety model for source creation and overwrite prompts.
   - Do not ignore sudo/root requirements.

5. Add tests with behavior changes.
   - Prefer the smallest relevant Go test package over a broad suite.
   - If behavior is user-visible CLI logic, test it in the relevant command package.

## Project-specific guardrails

Use this section for repository-specific coding expectations that are not universal but should always be followed by agents.

- Public Go functions, methods, types, and structs should include doc comments that start with the exported name.
  - Example: `// Check verifies whether a source is still supported for the target release.`
  - Example: `// SourceList stores the parsed apt source entries for a directory.`
- Keep comments brief and factual; do not add marketing language or repeated restatements.
- Prefer package-local helpers over new abstractions unless the abstraction is clearly reused.
- Preserve existing CLI UX and flag naming unless the change explicitly updates the documented behavior.
- Use semantic commit messages for changes and releases.
  - Use conventional prefixes such as `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`.
  - Do not invent custom prefixes or add generated signatures such as `Co-authored-by:`, `Signed-off-by:`, or `Generated by ...`.
  - Do not add AI or tool attribution lines to commit messages.
- Keep answers brief but informative.
  - Prefer a concise summary with enough detail to explain the decision, tradeoff, or validation.
   - If a user asks for a new feature, ask targeted clarifying questions before implementation unless the request is explicit enough to proceed without them.
   - If a request is ambiguous or offers multiple approaches/options, do not implement immediately.
   - In that case, run a short clarification interview first: compare each option by best-fit scenarios, advantages, disadvantages, compatibility impact, and implementation complexity.
   - End the interview by asking the user to choose a direction, then implement only after that choice is confirmed.
  - If the user has clearly specified a desired outcome, do not block on unnecessary questions.
  - If a user requests to change a user facing behavior ensure we also update the relevant documentation, tests, and prompts to reflect the new behavior. Only do that if the user explicitly request to change an existing feature. In the doubt ask for clarification.


## Canonical workflow

Use these commands as the default project workflow:

- make help
- make fmt
- make test
- make run ARGS="check noble"
- make build-cli VERSION=0.1.0

For a focused check, run the relevant package test first, then the wider suite if needed.

## Safety-specific constraints

- Do not combine --from-list-file and --from-list-entry in the same create command.
- Keep dry-run behavior explicit and non-destructive.
- Respect the project’s treatment of official Ubuntu sources and protected apt configuration.
- Do not assume a suite or distro name is a safe default for output filenames; prefer explicit or derived values and prompt when ambiguous.

## When in doubt

- Prefer existing project code and tests over new abstractions.
- Match the current implementation style instead of broad refactoring.
- Keep the change narrow, testable, and aligned with the README and Makefile.
